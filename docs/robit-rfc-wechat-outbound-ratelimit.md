## 1. 共同语境：一次真机事故与出站发送链路

### 1.1 事故（子木 2026-11-20 真机，ADR-0019 预警合并首测）

子木常驻服务 11:03:56 重启后，微信通道即报「已连接」，但 **11:04:01–11:05:13 微信所有出站发送持续失败**：

```
WeChat send failed: API error: errcode=-2, errmsg=prepare failed
```

期间调度器触发 10 条预警（子木已合并为一批）：**QQ 送达 1 条合并消息，微信同批失败丢失**。11:05:26 起微信出站自愈恢复。子木初判误以为是「重启使出站上下文失效、须新入站消息重建」，**经 SDK 文档核实推翻**（见 1.2）。

### 1.2 根因：服务端反刷限流（SDK 文档实锤，非假设）

外部协议 SDK `weixin-agent` 0.3 的 README「发送失败必须处理」节与 CHANGELOG 明记（生产实测）：

> **突发发送触发服务端反刷限制** → `{"ret":-2,"errmsg":"prepare failed"}`，此后**分钟级内该 bot 的所有发送都失败（与 `context_token` 无关）**，随后自愈。实测边界：**34 秒内 18 条会触发，170 秒内 10 条安全**。

据此核对 robit-wechat 源码，三点确认：

1. **是账号级服务端限流，重启清不掉**：限流挂在 bot 账号上、跨进程存续。子木重启后首条出站（11:04:01）仍失败，~90s 后自愈——与「分钟级自愈」吻合。
2. **与 context_token 无关**：`robit-wechat/src/platform.rs:158-159` 在 `connect` 时 `client.context_tokens().import(state.context_tokens.clone())` 从持久化状态恢复出站 token；入站时 `:277-279` 持续落档。**token 没丢，主动首发能力健在**。
3. **11:05:25 那条入站消息只是巧合**：恢复实为限流冷却到期，并非「新入站重建上下文」。

**突发源**（子木侧观察，供 robit 参考量级）：重启窗口积压 6 条入站一次性投递 → chatbot 串行快速回复（每回合含进度提示 + 答案，多工具回合更多）+ 调度器预警批推送，短时密集出站撞上阈值。

### 1.3 出站发送链路（行号 0.3.0 @ b9f82a0）

| 站 | 代码 | 行为 | 问题 |
|---|---|---|---|
| ① 回合内文本累积 | `robit-chatbot/src/frontend.rs:177-182` `append_delta` | TextDelta 入 buffer | — |
| ② 工具调用前 flush | `frontend.rs:312-318`（`on_event` ToolCallRequested 臂） | 先 `flush_buffer()`（:313）再 `send_progress_hint()`（:318，auto_approve） | **W2** |
| ③ flush 出站 | `frontend.rs:197-252` `flush_buffer` | 微信 `supports_edit=false` → 走 `:233` `send()` 独立发一条；每个有缓冲文本的工具前都 flush 一次 | **W2** |

| ⑥ adapter 出站 | `robit-wechat/src/platform.rs:447-459` `send_message` | `client.send_text(peer, text, token)`；**任何 SDK Err 一律 `AgentError::InternalError`**（:454） | **W1/W3** |

**净效果**：整条出站链**没有任何时间维度的速率控制**。微信因 `supports_edit=false`（`adapter.rs:127-133`）无法编辑合并，每次 flush / 进度提示都是独立 HTTP 发送——一个多工具回合 + 密集入站即可在数十秒内发出十几条，触发账号级反刷，进而**分钟级内该 bot 全部出站（含宿主主动推送）瘫痪**。进度提示的「每回合一次」布尔闸只防单回合重复，不防跨回合 / 跨消息的突发。

## 2. 诉求批 W1–W4

### W1 【健壮性·高】微信出站速率控制（核心诉求）

- **现象/证据**：`platform.rs:447-459` / `:482-501` 收到发送请求即调 SDK，无间隔、无令牌桶；SDK 文档明示突发会触发账号级反刷（34s/18 条触发，170s/10 条安全）。
- **影响**：任何密集出站场景（密集入站引发的密集回复、宿主批量主动推送、多工具回合）都可能触发限流，使该 bot **分钟级内所有出站失败**——包括与突发无关的宿主主动推送（子木预警批因此丢失）。这是「一条老鼠屎坏一锅汤」：突发惩罚波及全部出站。
- **诉求**：在 robit 自有层为微信出站加**速率控制**，把发送节奏守在 SDK 安全阈值内（建议缺省保守于「170s/10 条」，如平均间隔 ≥ 数秒 + 限制突发容量）。层位选项见 §3，**由 robit 拍板**。要点：
  - 限流粒度 = **bot 账号级**（与服务端惩罚粒度一致），不是 per-peer——否则多 peer 并发仍会叠加触发。
  - 文本与媒体两路（`send_message` / `send_media_message`）同守卫。
  - 速率参数宜可配置（缺省保守），并文档化其与 SDK 实测阈值的关系。

### W2 【展示/健壮性·中】单回合出站消息数收敛

- **现象/证据**：微信 `supports_edit=false`（`adapter.rs:129`）→ `flush_buffer` 走独立 send（`frontend.rs:233`）；`on_event` 在每个工具调用前 flush（:313）+ 进度提示（:318），TurnComplete 再 flush（:351）。一个 N 工具回合最多可产生「进度提示 1 + 中间 flush 若干 + 最终 flush 1」条独立消息。
- **影响**：单回合即放大出站条数，是 W1 突发的主要来源之一；SDK 文档亦建议「长回复应自行合并分片而非拆成大量小消息」。
- **诉求**：降低单回合出站条数。候选（robit 定）：
  - 进度提示与最终答案**合并**（或进度提示在微信面降级为不发——SDK 文档已述进度 item 微信客户端本就不渲染，见 weixin-agent README「出站 Run」节）；
  - 抑制工具间的中间 flush（缓冲到回合收口一次性发，或按自然边界少量分段）；
  - 与 W1 节流协同：即便条数多，也由节流摊平到安全节奏。
- **边界**：QQ 等 `supports_edit=true` 平台已用编辑合并（`frontend.rs:222-230`），本诉求主要针对无编辑能力的平台（微信），不应劣化 QQ 现行为。

### W3 【错误语义·中】-2 瞬态限流码类型化，区别于永久失败

- **现象/证据**：SDK 把 -2 转为 `Error::Api { errcode: -2, errmsg }`（`weixin-agent api/client.rs:77`），但 robit-wechat `platform.rs:454` / `:496` 把**任何** SDK Err 一律包成 `AgentError::InternalError(format!("WeChat send failed: {}", e))`——宿主在 adapter 边界**无法区分**「瞬态反刷（分钟级自愈）」与「永久失败（如 token 失效 -14、参数错误）」。
- **影响**：宿主只能一刀切。子木按 ADR-0011「推送失败不重试」纪律对 -2 也不重试 → 瞬态可恢复的丢失被当成永久丢失；反之若宿主盲目重试 -2 又会加深限流。错误语义缺失使宿主无法做正确决策。
- **诉求**：让 -2（及同类瞬态码）在 adapter 边界**可识别**。候选（robit 定）：
  - 映射为带语义的错误变体 / 标记（如 `AgentError::RateLimited { retry_after_hint }` 或在错误链保留 errcode），宿主据此区分瞬态与永久；
  - **可选**：adapter 级对 -2 做**冷却退避有界重试**（自愈后补发）。若做，须明确缺省策略与上限，并文档化「重试本身可能再触限流」的风险——**宿主侧是否允许重试属宿主纪律**（子木 ADR-0011 当前不重试，需另行拍板），robit 提供能力与缺省、宿主可关。
- **注**：-14（token 失效）已有专门处理（`platform.rs:337` `on_token_stale` 终态），本诉求只补 -2 这类**瞬态可自愈**码的语义，不动 -14 路径。

### W4 【可观测性·低】反刷限流的日志可辨识

- **现象/证据**：当前 -2 经 `platform.rs:454` 包成泛化 `WeChat send failed: API error: errcode=-2, errmsg=prepare failed`，日志无任何「这是服务端反刷、分钟级自愈、勿密集重试/勿重启」的提示。
- **影响**：子木本次即因日志不可辨识而**误判为「重启上下文失效」**，登记了错误根因（R14 初版），后据 SDK 文档才更正。可辨识的日志能避免消费方误判与无效操作（重启清不掉限流）。
- **诉求**：adapter 识别 -2 时输出明确 warn（含「服务端反刷限流 / 分钟级自愈 / 避免密集重试 / 重启无效」语义），与 W3 错误类型化天然同一处。

## 3. 选项与取舍（由 robit 拍板）

- **节流层位**：
  - **A · robit-wechat adapter 层**（倾向）：在 `send_message`/`send_media_message` 内或外包一个账号级令牌桶。优点——反刷是微信平台特性，放在平台 adapter 内聚、不污染通用 chatbot；QQ/飞书不受影响。缺点——每个有类似限制的平台各自实现。
  - **B · caps 驱动 + chatbot frontend 通用 pacing**：`PlatformCaps` 增速率字段（如 `min_send_interval` / `burst_capacity`），frontend 出站统一 pacing。优点——通用、平台声明式。缺点——通用层引入平台速率概念，且宿主主动推送（不经 frontend，直接调 adapter）仍需 adapter 层兜底，故 B 单独不够。
  - **C · A+B 组合**：adapter 层账号级硬守卫（兜住宿主直推）+ caps 声明供 frontend 优化节奏。最稳但工作量最大。
  - 子木倾向 **A 起步**（覆盖含宿主直推的全部出站），B/C 作后续增强；最终 robit 定。
- **-2 重试缺省**：开（adapter 自动冷却补发）vs 关（仅类型化、宿主自决）。涉及宿主纪律差异，robit 定缺省 + 提供开关。子木当前倾向**关**（先靠节流压低触发概率，避免越撞越深），待真实运行数据再议。
- **进度提示微信面**：合并 / 降级不发 / 保留但节流。SDK 已述微信客户端不渲染进度 item，倾向降级不发或合并。
- **速率参数缺省**：保守于 SDK 实测安全边界（170s/10 条），具体值 robit 定并文档化。

## 4. 验收标准

1. **节流生效**：构造密集出站（如短时连续 N 条 send_message），实际发送节奏被摊平到配置阈值内，不触发 -2（可用 mock SDK / 计数 + 时间断言离线验证）。
2. **账号级粒度**：多 peer 并发出站共享同一速率预算（不是每 peer 独立放行）。
3. **文本 + 媒体同守卫**：两路出站均受节流。
4. **-2 可识别**：adapter 边界能把 -2 与永久失败区分（类型化断言）；日志含反刷语义（W4）。
5. **QQ 零回归**：QQ 现行为（编辑合并、caps、数值）逐位不变（回归钉单测）。
6. **context_token 路径不动**：持久化 / 恢复 / 入站落档行为不变（本件非上下文问题）。
7. 若做 -2 重试：缺省策略 + 上限 + 可关断言；重试不无限加深限流。

## 5. 边界与非目标

- **不改外部 SDK `weixin-agent`**：它是 crates.io 协议层依赖（robit Cargo.toml:47 注释「纯协议层」），反刷是微信服务端行为，SDK 已正确把 -2 转 Err（非假成功）。防护落在 robit 自有层。
- **不渗宿主领域逻辑**：预警合并、推送订阅、不重试纪律等是子木宿主策略（ADR-0019/0011/C15），robit 只提供通用出站防护与错误语义，不内置任何宿主业务。
- **不动 QQ / 飞书**：反刷是微信 iLink 特性；QQ 无此问题，现行为保持。
- **非 context_token 问题**：主动首发能力健在（token 持久化恢复），本件不处理「冷首发」（R13 末项可据此勾销「主动首发被拒」的疑虑——真实拦路的是限流）。
- **重启不是解法**：限流账号级跨重启存续，文档与日志应明示，避免消费方误操作。

## 6. 子木侧现状与消费意向

- **已做**：预警轮内合并（ADR-0019，10 条→1 条）已削减最大突发源；`push_to_bound` 已正确把 SDK Err（含 -2）记 `push_log ok=false`，不静默丢（SDK 转 Err 而非假成功的纪律已对齐）。
- **零绕过**：子木未在宿主侧写绕过 adapter 的节流补丁（框架级缺口归 robit）；本次仅登记 R14 + 本移交件。
- **消费意向**：robit 发版后子木升版消费（纯升版或最小适配，视 API 变化）；W3 若提供 -2 重试能力，子木是否启用须另行拍板（ADR-0011 不重试纪律的例外）。
- **运维缓解**（子木侧、非代码，已记 R14）：避免短时密集给 bot 发消息；触发后等分钟级自愈，重启无效。
