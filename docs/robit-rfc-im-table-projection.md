## 1. 缺口：两平台都不渲染表格，现状一条漏原始语法、一条发错位伪表格

### 1.1 平台能力事实

- **QQ 官方 bot**（群聊/私聊文本消息）不渲染 Markdown 表格：`MarkdownFeatures::qq()`（adapter.rs:70-86）`tables: false`，仅 `code_blocks: true`。
- **微信 iLink 客户端**不渲染表格（子木 2026-11-22 真机实观）：`MarkdownFeatures::wechat()` = 全 false（adapter.rs:109-111），`PlatformCaps::wechat().supports_markdown = false`（adapter.rs:156）。
- **weixin-agent 0.3.0 SDK 有意保留表格**：`filter_markdown` 模块文档明写 "Preserves: code fences, inline code, **tables**, horizontal rules, bold, blockquotes…"（markdown_filter.rs:1-9），`table_preserved` 单测钉死管道表格字节级直通（:556-560）。SDK 移植自微信官方 npm 包，**假设客户端会渲染表格**——该假设在子木部署形态不成立。SDK 是上游依赖，本件不诉求 SDK 改动：**robit 投影层应在 SDK 之前把表格消化掉**。

### 1.2 两条泄漏路径（0.4.1 @ de26925）

| 入口 | 代码 | 现状 |
|---|---|---|
| **微信 chatbot 会话回复** | `frontend.rs:256-260` `flush_buffer`：`supports_markdown=false` → `text.clone()` **整体跳过清洗器** | ❌ 原始管道表格 → `prepare_outbound`（只管长度）→ SDK 保留表格 → **原始语法直达用户**（`\| a \| b \|` 与分隔行原样显示） |
| **QQ chatbot 会话回复** | 清洗器生效 → `render_table`（markdown.rs:276-312） | ⚠️ 空格补位对齐 + 竖线分隔 + `-+-` 分隔行的**伪表格**：对齐假设等宽字体，IM 客户端是比例字体 → 列错位；且宽度按 `chars().count()`（CJK 显示宽 2 列按 1 计）→ 等宽环境也不齐 |
| **宿主直调推送（调清洗器）** | 子木 `channel_push.rs` 显式调 `prepare_markdown_for_platform` | ⚠️ 双平台均得对齐伪表格形态（同上） |
| **宿主直调 `adapter.send_message`（不调清洗器）** | R16 同款覆盖面缺口 | ❌ 微信原始语法直达（长度守卫已透明，内容投影未透明） |

### 1.3 清洗器自身的 feature 不一致（纯文本模式的前置问题）

`MarkdownFeatures` 声明 13 个标志，但部分**从未被消费**（grep 实锤，markdown.rs 全文无消费点）：

| 标志/分支 | 现状 | 问题 |
|---|---|---|
| `features.tables` | **死标志**：表格分支（:174-200）不读它，恒走对齐文本 | 未来 `tables=true` 平台也不会直通原始语法 |
| `features.code_blocks` | **死标志**：代码块分支（:82-95）恒输出 ` ``` ` 栅栏 | 纯文本平台收到字面栅栏（微信 SDK 还保留栅栏） |
| `features.unordered_lists` / `ordered_lists` | **死标志**：列表分支（:108-117）恒输出 `- ` / `N. ` | 标记本身是自然纯文本约定，**可保留**（非缺陷，登记备查） |
| 标题降级（:73-75） | `headings=false` 时恒输出字面 `**`，**不尊重 `features.bold`** | QQ（bold=false）用户看到字面星号；微信靠 SDK 剥除兜底 |
| 引用降级（:137-140） | `blockquotes=false` 时输出字面 `> ` | 纯文本平台 Markdown 残留 |
| 链接降级（:155-157） | `links=false` 时**丢弃 URL** 只留文本 | 信息损失；是否改「文本 (url)」由 robit 定，非本件核心 |

**结论**：不能简单对微信启用现清洗器——all-false features 会产出字面 `**` 与 ` ``` `。需要真正的「纯文本投影」语义：**降级尊重 features**。

## 2. 诉求批 T1–T3

### T1 【核心】表格降级 = 线性化记录，不是网格复现

**原理**：IM 客户端字体不受控（比例字体），任何依赖对齐的形态原理性不可读。线性化不需要对齐——比例字体/CJK 宽度问题整个消失。这不是排版优化，是投影策略转变。

**规则建议**（确定性、可单测钉死；细节 robit 可调）：

- **两列表**（最常见的键值形态）→ 逐行 `列1: 列2` 行。
- **N 列表** → 逐记录线性化：首列作记录头，其余列 `表头: 值` 以 ` · ` 连接；记录间空行；宽表（>5 列）记录内拆多行防超长行。
- **空单元格**跳过该键值对（不输出 `表头: `）。
- 表头行不单独输出（语义已并入每个键值对）。
- **输出无表格语法残留**（无管道符、无分隔行）→ 二次投影幂等无操作。
- `features.tables=true` 的平台（未来）直通原始语法——**激活死标志**，分支语义补全。

**示例**（子木持仓回答，真实场景）：

```
模型输出：                              投影后（任何字体下可读）：
| 持仓     | 现价   | 盈亏   | 仓位  |    贵州茅台 — 现价: 105.00 · 盈亏: -4.59% · 仓位: 28.0%
|----------|--------|--------|-------|    五粮液 — 现价: 118.20 · 盈亏: -1.50% · 仓位: 15.2%
| 贵州茅台 | 105.00 | -4.59% | 28.0% |
| 五粮液   | 118.20 | -1.50% | 15.2% |
```

两列形态：`总资产: 290362.30` / `仓位: 68.9%` 逐行。

### T2 【覆盖面】纯文本平台也过投影（堵微信绕过）

- `flush_buffer` 去掉 `supports_markdown=false` 的跳过分支（frontend.rs:256-260）：清洗器定位是「平台可读性投影」而非「Markdown 渲染器」，**all-false features = 纯文本投影**，本就该跑。
- **前置**：降级尊重 features（§1.3）——`bold=false` 时标题降级输出纯文本 + 空行（不输出 `**`）；`code_blocks=false` 时栅栏标记去除、代码内容保留；引用降级去字面 `> `。列表标记 `- ` / `N. ` 保留（纯文本自然约定）。
- 改完微信输出与 caps 宣称一致（caps 说纯文本，输出就是纯文本）；SDK `filter_markdown` 变成无害二次过滤——它「保留」的表格/栅栏/加粗已被投影掉，无冲突。
- **行为变化明示**：微信非表格输出也随之变化（加粗标记去除、栅栏去除等）——这是语义决策，robit 拍板。**子木立场：caps 诚实优先**，现状「宣称纯文本却发原始 Markdown」才是缺陷。
- QQ 路径（`supports_markdown=true`）行为除 T1 表格外逐位不变（既有单测回归钉）。

### T3 【可选，R16 同款】投影下沉 adapter 直调路径

- 扩展 `prepare_outbound`（outbound.rs:73）为「**内容投影 + 长度守卫**」统一出站准备（或并列 `prepare_content` 在同咽喉调用）：不调清洗器的宿主直调也自动获得平台可读投影——与 R16 长度守卫透明封装完全同构，出站保障补完整。
- **幂等**：线性化文本无表格语法、纯文本无 Markdown 标记，二次投影无操作；chatbot 回复路径（已过清洗器）行为逐位不变。
- 若不做：trait 文档写明「直调方应自行调 `prepare_markdown_for_platform`」（子木推送链已显式调，T1 落地即覆盖；但每个新宿主都要自己记得调——R16 前的长度守卫同款困境）。
- **子木倾向做**（透明封装一致性）；robit 拍板。

**辅助手段（可选，不能替代投影）**：按 caps 向系统提示词注入渠道格式提示（「当前渠道纯文本，避免表格」），从源头减少表格产出。模型服从性不保证，确定性投影仍是兜底——两条腿走路，robit 定要不要。

### 不建议的路径（评估过，留档）

| 路径 | 判断 |
|---|---|
| CJK 宽度感知对齐（unicode-width） | 只治等宽环境；IM 客户端比例字体，治标不治本 |
| 表格渲染成图片发送 | 双平台能发图、保真完美，但引入字体渲染依赖/延迟/文本不可复制——个人助理场景过度设计，留作最后手段 |
| QQ markdown 卡片（ark 模板） | 需官方模板审核，自由表格不可行，非通用解 |

## 3. 验收标准（建议）

1. **线性化单测**（robit-chatbot markdown.rs）：两列/N 列/宽表/空单元格黄金字符串；输出无管道符与分隔行残留；**二次投影幂等**（输出再过一遍逐字节不变）；`features.tables=true` 直通原始语法。
2. **纯文本投影单测**：all-false features 输入（标题/加粗/代码栅栏/引用/表格）→ 输出无字面 Markdown 标记（列表标记除外）；QQ features 既有单测迁移后除表格外逐位不变。
3. **flush_buffer 集成**：微信 mock 含表格回复 → 底层发送内容为线性化形态（无原始管道语法）；QQ 回复路径回归。
4. **（若 T3 采纳）直调组合**：长表格文本直调 → 投影 + 分段组合正确（R16 单测形态扩展）；≤cap 已投影文本幂等直通。
5. **真机**（子木侧，发版后）：同一含表格回答 → Web 正常渲染表格 / 微信收到线性化记录 / QQ 同款；无原始管道语法、无错位伪表格。
